# 物品堆积/异常占用检测（区域遗留物引擎）详细设计

> 版本：v1.1（设计稿）
> 日期：2026-10-13
> 状态：待评审
> v1.1 变更：产品形态拆分为两种检测类型（物品堆积检测 / 异常占用检测），底层共用同一引擎

---

## 1. 背景与目标

### 1.1 需求

- **物品堆积检测**：门口、角落等区域出现堆积物（垃圾、纸箱、杂物，类型不固定）时告警
- **异常占用检测**：消防通道、车道、人行道等"应保持空旷"的区域被占用时告警

### 1.2 产品形态：两种检测方式

系统对外提供**两种独立检测类型**（任务创建下拉可选）：

| 检测类型 | detection_type / event_type | 语义 | 典型场景 |
|---|---|---|---|
| 物品堆积检测 | `pile_up` | 区域内出现堆积物且持续存在 | 门口/角落垃圾、纸箱堆积；堆积形成慢，允许较长确认时间 |
| 异常占用检测 | `abnormal_occupancy` | 区域被异常占用且持续存在 | 消防通道被占、车道被堵；需要较快响应 |

两者底层统一为**区域遗留物引擎**（同一套差分判定 + 状态机）：配置"应保持空旷"的多边形区域，
任何物体出现且**持续存在**超过时长阈值即告警，物体移走后恢复。两种检测类型的差异仅在
事件语义与默认参数，引擎、管线、基线管理代码完全共用。

### 1.3 关键决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 检测手段 | 背景差分（侦差法），不依赖目标检测模型 | 占用物/堆积物类型开放，COCO 类不覆盖"杂物"；差分类无关、零模型成本 |
| 产品形态 | 两种检测类型 `pile_up` / `abnormal_occupancy`，共用同一引擎 | 对外语义清晰（堆积≠占用），默认参数与事件类型独立；实现零重复 |
| 基线来源 | **任务管线内部取帧**（解码输出），不使用 `/snapshot/<camera_id>` 接口 | 基线必须与运行时参与比对的帧同源、同尺寸、同色彩格式；`/snapshot` 走独立 ffmpeg 抓帧，分辨率/色彩范围与管线帧不一致 |
| 基线采集方式 | 人工确认场景空旷后触发"拍摄基线"，连取 5 帧逐像素取中值 | 基线由人确认无冷启动误判；多帧中值消除路过的行人和瞬时噪声 |
| 差分颜色空间 | Y 平面（亮度）差分 | 与现有运动检测（`y_plane`）一致，免 YUV→RGB 转换开销；亮度差分对物体出现/移走敏感 |
| 事件链路 | 复用现有事件系统（事件表/MQTT/推送/GIF） | 新增 `pile_up` / `abnormal_occupancy` 两种事件类型，与 `people_counting` 同模式扩展 |

## 2. 总体架构

```
┌─────────────────────────── 任务子进程（CameraWorker）───────────────────────────┐
│                                                                                 │
│  VideoDecoder (6fps, 共享内存 ring buffer)                                       │
│        │ read_frame_i420 → (header, y_plane, u_plane, v_plane)                  │
│        ▼                                                                        │
│  occupancy_pipeline.run_occupancy_pipeline()                                    │
│        │  每 OCCUPANCY_INTERVAL_FRAMES=6 帧执行一次（≈1s/次）                     │
│        ▼                                                                        │
│  OccupancyAnalyzer（每通道一个实例）                                              │
│    ├─ BaselineManager     基线加载/拍摄/存储                                      │
│    ├─ DiffAnalyzer        差分计算（mask/归一化/形态学/面积占比/全局突变判定）      │
│    └─ ZoneOccupancyState  每区域独立状态机                                        │
│        │  状态迁移时产出消息                                                      │
│        ▼                                                                        │
│  detected_objects_queue.put(遗留物消息 dict)                                     │
│                                                                                 │
│  控制输入：共享控制字典 flag → capture_baseline 请求                               │
└─────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌────────────────────── 事件进程（TrackedObjectProcessorPool）─────────────────────┐
│  _process_detection_data():                                                     │
│    ├─ tuple 消息 → 现有目标事件流程（不变）                                       │
│    └─ dict 消息且 __type__='occupancy' → _on_occupancy_message()                 │
│          ├─ alert    → 创建事件（shm 回读快照 + 事件表 + MQTT/推送/GIF 可选）      │
│          ├─ recovery → 结束事件（可选恢复通知）                                    │
│          └─ global_change → 前端 Socket.IO 提示重拍基线（不产生告警事件）          │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**要点**

- 新增两种 detection_type：`pile_up`（物品堆积检测）、`abnormal_occupancy`（异常占用检测），
  均映射同一管线函数 `run_occupancy_pipeline`，**不加载检测模型、不开运动检测、不开跟踪**，不占用检测池与 NPU
- 事件类型与 detection_type 同名（`pile_up` / `abnormal_occupancy`），沿用 people_counting
  "检测类型即事件类型"的既有模式
- 状态机运行在管线进程（持续持有解码帧）；事件生成与输出复用事件进程现有链路
- 基线按**通道**存储（同一相机同一画面），任务重启后基线仍然有效，无需重拍

## 3. 核心算法设计

### 3.1 基线采集

触发方式：前端"拍摄基线"按钮 → API → 共享控制字典标志 → 管线进程执行。

```
采集流程（occupancy_pipeline 内响应 capture_baseline 标志）:
1. 连续取 5 帧 Y 平面（间隔约 0.5s，覆盖 2~3 秒窗口）
2. 逐像素取中值 → baseline_y (H×W uint8)
3. 缩放规则与运行时帧一致（同一解码链路，天然对齐，无需缩放）
4. 落盘:
   - data/baselines/{channel_id}.jpg    # 灰度 JPEG（基线本体）
   - data/baselines/{channel_id}.json   # 元数据 {captured_at, frame_shape, task_id}
5. Socket.IO emit 'baseline_captured' {task_id, channel_id}
```

- 多帧中值的目的：消除拍摄瞬间路过的人/车、传感器噪声
- 每通道一张基线；多区域共用该基线，运行时按各自多边形 mask 取 ROI
- 任务启动时若存在启用区域但基线文件不存在 → 状态 `UNCALIBRATED`，不告警，API/前端提示"请拍摄基线"

### 3.2 差分计算（每秒一次，逐区域）

```
DiffAnalyzer.analyze(current_y, baseline_y, zone_mask):
1. ROI 裁剪:   取 zone polygon 外接矩形（含 4px 边距）
2. 亮度归一化: current_roi = (current_roi - mean_c) * (std_b / std_c) + mean_b
               （吸收白平衡漂移/JPEG 色彩范围差等全局亮度偏移）
3. 绝对差分:   diff = |current_roi - baseline_roi|
4. 二值化:     mask_diff = diff > DIFF_THRESHOLD(25)
5. 多边形掩膜: mask_diff &= zone_polygon_mask（只统计区域内像素）
6. 形态学:     开运算(3×3)去孤立噪点 → 闭运算(5×5)连片
7. 面积占比:   ratio = mask_diff 像素数 / zone_mask 像素数
```

### 3.3 判定规则（三区段）

| 差异占比 ratio | 判定 | 行为 |
|---|---|---|
| < `min_area_ratio`（默认 0.02） | 空旷 | 计入"连续空旷时长" |
| `min_area_ratio` ~ `global_change_ratio`（默认 0.60） | 疑似遗留物 | 进入/维持候选，累计持续时长 |
| ≥ `global_change_ratio` | 全局环境突变 | 判定为光照切换/相机位移，**不告警**，迁移 `INVALID` 状态，Socket.IO 提示重拍基线 |

全局突变取该通道**所有区域**的最大 ratio 判定（相机位移/昼夜切换时全画面差异，任何区域都会超限）。

### 3.4 区域状态机

```
                 ┌──────────────────────────────────────────────┐
                 │                                              │
                 ▼                                              │
   ┌─────────────────────┐   ratio≥min 持续达 dwell_seconds    ┌──────────────────┐
   │  MONITORING 监测中   │ ──────────────────────────────────► │  ALERTED 已告警   │
   │  （含 CANDIDATE      │                                     │  创建事件+冻结基线 │
   │   候选累计阶段）      │ ◄────────────────────────────────── │  不重复告警       │
   └─────────────────────┘   ratio<min 持续 clear_confirm_s    └──────────────────┘
                 │                    + 可选恢复通知
                 │ 0.6s内短暂跌落不重置（grace_seconds=5 抗抖动）
                 │
   ┌─────────────────────┐
   │ UNCALIBRATED 未校准  │  无基线，等待拍摄；全局突变 → INVALID（同需重拍）
   │ INVALID 基线失效     │
   └─────────────────────┘
```

状态定义：

| 状态 | 含义 | 行为 |
|---|---|---|
| `UNCALIBRATED` | 无基线 | 不判定不告警；API 状态可见 |
| `MONITORING` | 监测中 | 差分评估；候选时长累计（dwell 计时）；突变 → INVALID |
| `ALERTED` | 已告警 | 事件保持打开；基线**冻结**不更新（防止堆积物被吸收为背景）；不重复告警 |
| `INVALID` | 基线失效 | 全局突变后进入；不告警；等待重拍（或人工确认后恢复 MONITORING） |

状态迁移关键参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `dwell_seconds` | 按任务类型：`pile_up` 300 / `abnormal_occupancy` 60 | 候选→告警的持续时长阈值（区域级可覆盖） |
| `grace_seconds` | 5 | 候选期间差异短暂跌落到阈值下的容忍窗口（行人遮挡/抖动），不重置计时 |
| `clear_confirm_seconds` | 30 | 差异持续低于最小阈值该时长才判定"已移走"，防瞬时遮挡误恢复 |
| `min_area_ratio` | 0.02 | 最小面积占比门槛（区域级可覆盖；按区域大小调 0.01~0.05） |
| `global_change_ratio` | 0.60 | 全局突变判定线 |
| `DIFF_THRESHOLD` | 25 | 像素差分二值化阈值（灰度 0-255） |

### 4.2 关键接口

```python
# src/occupancy/baseline_manager.py
class BaselineManager:
    """基线管理：按通道存取，路径 data/baselines/{channel_id}.jpg"""

    @staticmethod
    def exists(channel_id) -> bool
    @staticmethod
    def load(channel_id) -> Optional[np.ndarray]            # 返回 Y 平面 (H,W) uint8
    @staticmethod
    def save(channel_id, baseline_y: np.ndarray, meta: dict)
    @staticmethod
    def capture_median(y_planes: list[np.ndarray]) -> np.ndarray  # 5 帧逐像素中值

# src/occupancy/diff_analyzer.py
class DiffAnalyzer:
    """差分分析，纯函数无状态"""

    def __init__(self, diff_threshold=25)
    def analyze(self, current_y, baseline_y, polygon_px) -> DiffResult
    # DiffResult: dataclass(area_ratio, mask, bbox)  bbox 为差异主连通域外接框（供事件图标注）

# src/occupancy/occupancy_state.py
class ZoneOccupancyState:
    """单区域状态机"""

    def __init__(self, zone_name, dwell_seconds, min_area_ratio, ...)
    def update(self, ratio: float, now: float) -> Optional[str]
    # 输入本秒面积占比，返回状态迁移: 'alert' / 'recovery' / None
    def state(self) -> str

class ChannelOccupancyMonitor:
    """通道级聚合：持有 BaselineManager + 每区域 ZoneOccupancyState"""

    def __init__(self, channel_id, detection_type, zones_config, frame_shape)
    # detection_type 决定: 筛选 enable_pileup / enable_occupancy 区域 + 分类型默认 dwell
    def process_frame(self, y_plane, now) -> list[dict]     # 返回本帧产生的迁移消息
    def handle_global_change(self, now)                     # 全部区域 → INVALID
    def request_capture(self) -> bool                       # 置采集标志，管线循环响应
```

## 5. 与现有系统的集成点

### 5.1 管线注册 — `src/pipeline/pipeline_factory.py`

- `VALID_DETECTION_TYPES` 增加 `'pile_up'`、`'abnormal_occupancy'`
- `get_pipeline()` 两个类型均映射 `run_occupancy_pipeline`（延迟导入，同现有模式）

### 5.2 组件注入 — `src/tasks/task_executor.py`

`detection_type ∈ ('pile_up', 'abnormal_occupancy')` 时：

- `motion_detector=None`、`tracker=None`、`remote_detector=None`（不初始化检测器，不占用检测池）
- 其余（共享内存、心跳、结果队列、停止事件）与现有 CameraWorker 完全一致，自动继承心跳自愈机制
- `camera_configs` 注入时携带 `zones_config`、`control_flags` 与 `event_type=detection_type`

### 5.3 事件链路 — `src/events/tracked_object_processor.py`

`_process_detection_data()` 入口增加消息类型分支（向后兼容，tuple 照旧）：

```python
if isinstance(data, dict) and data.get('__type__') == 'occupancy':
    self._on_occupancy_message(data)
    return
```

`_on_occupancy_message()` 处理三类消息：

| 消息 event | 处理 |
|---|---|
| `alert` | 复用 `_read_frame_from_shm(shm_info)` 取告警帧快照 → 创建事件记录（event_type=`pile_up` / `abnormal_occupancy`，随任务 detection_type；附 zone_name/area_ratio/dwell_seconds/diff_bbox）→ 走现有事件输出（事件表 + MQTT + 推送，GIF 可配置关闭——静态堆积物 GIF 价值低） |
| `recovery` | 结束对应事件；`event_config.occupancy_recovery_notify` 开启时发送恢复通知（同事件 ID 追加一条恢复记录/推送） |
| `global_change` | Socket.IO emit `baseline_invalid` {task_id, channel_id}，前端提示重拍基线，不产生告警事件 |

- 事件去重：`ALERTED` 状态期间状态机本身不重复发 `alert`，天然单事件
- 语音播报（可选）：`voice_alarm.type_audio_map` 增加 `pile_up` / `abnormal_occupancy` 项，复用现有 AlarmPlayer

### 5.4 队列消息格式

遗留物消息为 dict（与现有 9 元组区分，`isinstance` 判定，零歧义）：

```python
{
    '__type__': 'occupancy',
    'camera_id': str,
    'detection_type': 'pile_up' | 'abnormal_occupancy',
    'event': 'alert' | 'recovery' | 'global_change',
    'zone_name': str,
    'area_ratio': float,          # 触发时差异占比
    'dwell_seconds': int,         # 实际持续秒数
    'diff_bbox': [x1,y1,x2,y2],   # 差异主连通域外接框（事件图标注用，alert 时有效）
    'shm_block_id': str,          # 触发帧块 ID（供事件进程回读快照）
    'sequence_num': int,
    'timestamp': float,
}
```

### 5.5 区域配置扩展 — `device_channel_pool.zones_config`

区域为通道级（现状不变），`zones_config` 每项新增**可选**字段（JSON 内扩展，无 DB 迁移）：

```json
{
  "name": "消防通道",
  "polygon": [[0.1,0.1], [0.9,0.1], [0.9,0.9], [0.1,0.9]],
  "enable_pileup": true,
  "enable_occupancy": true,
  "pileup_dwell_seconds": 300,
  "occupancy_dwell_seconds": 60,
  "min_area_ratio": 0.02
}
```

- `_validate_zones_config()`（[task_api.py](file:///e:/sagesight-ai/src/tasks/task_api.py#L898)）增加上述可选字段的类型校验（2 个 bool、2 个 10~86400 整数、1 个 0.001~0.5 浮点）
- **分类型开关**：`enable_pileup` / `enable_occupancy` 控制该区域分别参与哪种检测，避免同区域双重告警
- `pile_up` 任务只读取 `enable_pileup=true` 的区域，`abnormal_occupancy` 任务只读取 `enable_occupancy=true` 的区域；任务启动时无启用区域则告警提示
- 区域未配置 dwell 时使用任务类型默认值（pile_up 300s / abnormal_occupancy 60s）
- 与现有 `enable_loitering_detection`（徘徊）互不影响：同一区域可同时开启，各自独立判定

### 5.6 基线采集 API — `src/tasks/task_api.py` 新增

| 接口 | 说明 |
|---|---|
| `POST /api/tasks/<task_id>/capture-baseline` | 请求拍摄基线。任务必须处于运行中且 `detection_type ∈ ('pile_up', 'abnormal_occupancy')`，否则 400。置共享控制字典标志，管线进程下一循环响应 |
| `GET /api/tasks/<task_id>/baseline-status` | 返回各通道基线与区域状态：`[{channel_id, baseline_captured_at, state, zones: [{name, state, last_alert_at}]}]`。数据来源：任务进程定期（5s）回写共享字典的状态摘要 |

流程时序：

```
前端按钮 → POST capture-baseline → task_manager → 共享 control_flags['capture_baseline_{camera_id}']=True
       → occupancy_pipeline 下一秒响应: 连取 5 帧 → 中值 → 落盘 → 状态回写
       → Socket.IO emit 'baseline_captured' → 前端刷新状态徽标
```

任务未运行时请求拍摄 → 400「任务未运行，请先启动任务后再拍摄基线」（基线必须来自管线解码链路，无法离线补拍）。

## 7. 异常与边界场景

| 场景 | 行为 |
|---|---|
| 任务启动无基线 | `UNCALIBRATED`，不告警；前端徽标提示拍摄 |
| 运行中基线文件被删 | 下次重启任务转 UNCALIBRATED；运行中不受影响（基线已在内存） |
| 昼夜切换/开灯 | 全区域 ratio>0.6 → `INVALID` + Socket.IO 提示重拍（不误报） |
| 相机被碰/云台移动/变焦 | 同上（全画面错位超限） |
| 行人短暂经过 | 差异持续 < dwell，候选阶段自行回落，不告警 |
| 堆积物部分被移走 | ratio 降到 min 以下持续 30s → 恢复；若仍有残留则保持 ALERTED |
| 两个区域重叠 | 各自独立 mask 与状态，互不干扰 |
| 同通道同时运行堆积与占用两个任务 | 各任务独立管线进程与状态机；按区域 `enable_pileup` / `enable_occupancy` 开关分工，避免同一区域双重告警 |
| 通道更换相机（视图变化） | 基线文件属于旧视图 → 提示重拍；`baseline_captured_at` 供人工判断 |
| 任务重启 | 基线持久化在磁盘，重启直接进入 MONITORING（若此前已告警，事件以恢复/超时收尾，不重报——重启后状态机从 MONITORING 起步） |
| 多通道任务 | 每通道独立 monitor 实例与基线 |

## 8. 性能预算

| 项 | 开销 |
|---|---|
| 差分计算（640×640 Y 平面 absdiff + 阈值 + 形态学 + 2~3 区域 mask） | ≈2~5ms / 秒，纯 CPU |
| 基线拍摄（5 帧中值） | 一次性 ≈50ms |
| 内存 | 基线 + 缓存帧 < 5MB / 通道 |
| NPU / GPU | **零占用**（不加载检测模型） |
| 检测池 / 事件队列 | 遗留物消息量极低（仅状态迁移），队列压力可忽略 |

对现有实时检测任务无任何影响（独立管线类型）。

### 9.2 手工验收清单

1. 创建「物品堆积检测」任务 → 画区域（启用堆积）→ 启动 → 状态显示"未校准"
2. 拍摄基线 → 状态转"监测中"（空旷期间无告警）
3. 放置纸箱 → 达到 dwell 后产生 `pile_up` 事件（快照正确、MQTT 上报、事件列表可见）

7. 切换昼夜/遮挡镜头 → 基线失效提示，无误报
8. 重启任务 → 基线仍有效，无需重拍
9. 真机（RK3588 + CUDA 各一台）跑通全流程，确认 CPU 占用无感知

### 二期（数据驱动后按需启动）

| 项 | 说明 |

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 阴影/水渍导致局部持续假差异 | 形态学滤波 + 差分方向判断（可选，二期）；min_area_ratio 调参；误报→重拍基线闭环 |
| 客户场景"合法常驻物"（长期停放的叉车等） | 拍基线前人工清场（操作规程）；二期误报标记重学后常驻物自然进入基线 |
| 多任务共用通道时 zones_config 语义冲突 | zones_config 本就是通道级唯一数据源；分类型开关（enable_pileup/enable_occupancy）明确分工，与徘徊/进出互不干扰 |
| 恢复判定误报（物体被遮挡 30s） | clear_confirm 可调大；恢复通知可关闭 |
