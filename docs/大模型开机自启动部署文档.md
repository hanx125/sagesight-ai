# 大模型开机自启动部署文档

本文档说明如何在 RK3588 盒子上部署本地多模态大模型（Qwen3.5-0.8B）推理服务，并通过 systemd 实现开机自启动。

该服务为平台的事件描述与语义去重提供本地推理能力（OpenAI 兼容接口），部署完成后平台通过 `http://127.0.0.1:8002/v1` 调用，不依赖外网。

> **重要提示**：本机（RK3588，无 CUDA）**不能**用 Transformers + PyTorch 加载 HF 原始权重运行该模型，实测推理速度仅 0.09 tok/s，完全不可用。必须改用**方案二：llama.cpp + GGUF 量化**，详见第一章。

## 一、方案选型（为什么不能用 PyTorch）

### 方案一（已废弃）：Transformers + PyTorch + HF safetensors

最初按常规方式在盒子上建 venv 装 `torch` + `transformers`，直接加载 HuggingFace 原始权重（safetensors 1.7GB）。

实测结果：

| 指标 | 实测值 |
| --- | --- |
| 推理速度 | **0.09 tok/s** |
| 生成一句话（约 30 token） | 约 5 分钟 |
| 可用性 | **不可用** |

根因（不是配置问题，是架构问题）：

- **Qwen3.5 是混合线性注意力架构**，文本塔 24 层中按 `linear_attention × 3 + full_attention × 1` 循环，核心是 Gated Delta Networks (GDN)。其高效实现依赖 `flash-linear-attention` / `causal-conv1d` 两个库，而这两个库**只有 CUDA / Triton 后端，CPU 上没有 fast path**，只能退化成极慢的参考实现。
- **bf16 权重在 CPU 上缺少 `mkldnn_matmul` 支持**，无法走优化的矩阵乘路径。
- RK3588 只有 NPU/RGA，**没有 CUDA**，上述两个库根本无法编译启用。

因此方案一在 RK3588 上没有任何优化空间，只能整体放弃。

### 方案二（当前采用）：llama.cpp + GGUF 量化

改用 llama.cpp 的 `llama-server`，加载 GGUF 量化权重（`Q4_K_M`），走 CPU + NEON 优化路径。

同样的模型、同样的硬件，效果对比：

| 方案 | 运行时 | 权重格式 | 速度 | 结论 |
| --- | --- | --- | --- | --- |
| 方案一 | PyTorch + Transformers | HF safetensors (bf16) | 0.09 tok/s | 不可用 |
| **方案二** | **llama.cpp `llama-server`** | **GGUF Q4_K_M** | **16-18 tok/s** | **可用** |

**提升约 190 倍**。同时磁盘占用从 1.7GB 降到 0.75GB（`532MB` 模型 + `205MB` 视觉投影）。

> 结论：**盒子上部署该模型必须走 llama.cpp + GGUF**，不要再用 torch 方案。

## 二、前置条件

| 项目 | 要求 |
| --- | --- |
| 硬件 | RK3588 / aarch64，8 核 CPU，内存 ≥ 3.8GB（**板载 LPDDR，一般不可扩容**） |
| 系统 | Ubuntu 22.04 LTS，**需关闭图形桌面**（切到 `multi-user.target`，见第六章） |
| 内存余量 | 部署前 `free -m` 的 `available` 应 ≥ 1.5GB；模型本身还需约 1.1GB |
| 磁盘 | `/root` 所在分区可用空间 ≥ 3GB |
| llama.cpp | **必须包含 Qwen3.5 架构支持**（`LLM_ARCH_QWEN35`），即 2026-09-30 及之后的 master（本次使用 commit `eae11d22`） |
| 网络 | 盒子需能访问 `github.com` 与 `hf-mirror.com`（`huggingface.co` 在国内不通，用镜像） |

### 依赖安装

```bash
apt-get update
apt-get install -y build-essential cmake git
```

## 三、配置 swap

盒子物理内存仅 3.8GB，模型常驻约 1.1GB，为留出余量需加 4GB swap：

```bash
# 1. 创建 4G swap 文件
dd if=/dev/zero of=/swapfile bs=1M count=4096
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile

# 2. 写入 fstab 实现开机自动挂载
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 3. 验证
swapon --show
free -m
```

预期输出：

```
NAME      TYPE SIZE USED PRIO
/swapfile file   4G 548M   -2
```

## 四、编译 llama.cpp

```bash
# 1. 拉取源码（需含 qwen35 支持）
git clone https://github.com/ggml-org/llama.cpp /root/llama.cpp
cd /root/llama.cpp
git log -1 --format="%H %ad %s" --date=short
# 确认日期 ≥ 2026-09-30

# 2. 编译（只需 llama-server 与 llama-cli）
cmake -B build -DCMAKE_BUILD_TYPE=Release \
  -DLLAMA_CURL=OFF \
  -DLLAMA_BUILD_TESTS=OFF \
  -DLLAMA_BUILD_EXAMPLES=OFF \
  -DGGML_NATIVE=ON
cmake --build build --target llama-server llama-cli -j8
```

### 设计说明

- **`-DGGML_NATIVE=ON`**：按当前 CPU（RK3588 的 Cortex-A76/A55）启用 NEON 等指令集优化，是达到 16-18 tok/s 的关键。
- **`-DLLAMA_CURL=OFF`**：模型文件已提前下载到本地，不需要运行时下载能力，避免额外依赖 libcurl。
- **`-DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF`**：只编译必需目标，减少编译时间与磁盘占用。
- **`git clone` 在盒子本地执行**：不依赖从 PC 传源码，避免交叉编译工具链问题。

编译产物：`/root/llama.cpp/build/bin/llama-server`

## 五、下载模型文件

模型来源：`unsloth/Qwen3.5-0.8B-GGUF`（通过 `hf-mirror.com` 镜像）。

需要两个文件，**缺一不可**：

| 文件 | 作用 | 字节数 |
| --- | --- | --- |
| `Qwen3.5-0.8B-Q4_K_M.gguf` | 量化后的模型权重（文本塔 + 视觉塔） | 532,517,120 |
| `mmproj-F16.gguf` | 视觉投影层（多模态必需，缺了就无法读图） | 204,987,232 |

```bash
mkdir -p /root/qwen3.5-0.8b/gguf
cd /root/qwen3.5-0.8b/gguf

curl -L -o Qwen3.5-0.8B-Q4_K_M.gguf \
  https://hf-mirror.com/unsloth/Qwen3.5-0.8B-GGUF/resolve/main/Qwen3.5-0.8B-Q4_K_M.gguf

curl -L -o mmproj-F16.gguf \
  https://hf-mirror.com/unsloth/Qwen3.5-0.8B-GGUF/resolve/main/mmproj-F16.gguf

# 校验字节数必须与上表完全一致
ls -l
```

### 设计说明

- **`mmproj-F16.gguf` 不能省**：这个模型是多模态（视觉塔 depth=12、patch_size=16、spatial_merge_size=2），没有 mmproj 就只是一个纯文本模型，事件描述与语义去重（都需要看图）全部失效。
- **选 `Q4_K_M`**：0.75B 参数下 Q4_K_M 是质量与体积的平衡点。更高的量化（Q5/Q6）在盒子上只会更慢，更低的（Q3/Q2）会明显损伤图片描述质量。
- **用 `hf-mirror.com` 而不是 `huggingface.co`**：国内直连 `huggingface.co` 不通（curl 返回 000），镜像可稳定跑到约 3MB/s。

最终目录结构：

```
/root/qwen3.5-0.8b/
├── gguf/
│   ├── Qwen3.5-0.8B-Q4_K_M.gguf     (532,517,120 字节)
│   └── mmproj-F16.gguf              (204,987,232 字节)
└── service.log                       (运行日志，由服务文件指定)
```

## 六、服务文件内容

创建服务文件 `/etc/systemd/system/qwen3.5.service`，写入以下内容：

```ini
[Unit]
Description=Qwen3.5-0.8B local multimodal inference service (llama.cpp, OpenAI compatible)
After=network.target
StartLimitIntervalSec=300
StartLimitBurst=2

[Service]
Type=simple
WorkingDirectory=/root/llama.cpp
Environment=LD_LIBRARY_PATH=/root/llama.cpp/build/bin
ExecStart=/root/llama.cpp/build/bin/llama-server -m /root/qwen3.5-0.8b/gguf/Qwen3.5-0.8B-Q4_K_M.gguf --mmproj /root/qwen3.5-0.8b/gguf/mmproj-F16.gguf --alias Qwen3.5-0.8B --host 0.0.0.0 --port 8002 -c 4096 --parallel 1 -t 6 --jinja --reasoning off --image-max-tokens 128
Restart=on-failure
RestartSec=60
OOMScoreAdjust=500
MemoryMax=2400M
StandardOutput=append:/root/qwen3.5-0.8b/service.log
StandardError=append:/root/qwen3.5-0.8b/service.log

[Install]
WantedBy=multi-user.target
```

> **`StartLimitBurst` / `MemoryMax` / `OOMScoreAdjust` 三项不能省**。这不是性能优化，而是防止服务在内存不足时把**整台盒子拖死**的保险，原因见第六章末「内存预算与 OOM 防护」。

### ExecStart 参数说明（每一项都对应一个实测踩坑）

| 参数 | 作用 | 不配的后果 |
| --- | --- | --- |
| `-m .../Qwen3.5-0.8B-Q4_K_M.gguf` | 主模型权重 | — |
| `--mmproj .../mmproj-F16.gguf` | 加载视觉投影层，开启多模态 | 无法读图，描述/去重全部失效 |
| `--alias Qwen3.5-0.8B` | 对外暴露的模型名 | 需与平台配置里的 `model` 字段一致 |
| `--host 0.0.0.0 --port 8002` | 监听端口 | 平台默认连 `127.0.0.1:8002` |
| `-c 4096` | 上下文长度 | 太小装不下图像 token 会直接 400；**太大会显著抬高常驻内存**（`-c 8192` 实测多占约 1GB） |
| `--parallel 1` | 单并发槽位 | 多槽位会按倍数分摊 `-c`，导致每槽上下文不足 |
| `-t 6` | 推理线程数 | 8 核全占会挤占检测/解码线程 |
| `--jinja` | 启用 chat template | 多模态对话模板拼装错误 |
| **`--reasoning off`** | **全局关闭思考模式** | **模型把内容写进 `reasoning_content`，平台只读 `content` 会拿到空字符串** |
| **`--image-max-tokens 128`** | **限制单图视觉 token 数** | **1920×1080 原图单次推理 74 秒；同时也是压住内存峰值的关键开关** |
| **`MemoryMax=2400M`** | **cgroup 内存硬上限** | 超出时只在 cgroup 内 OOM 杀掉 llama-server，**不会牵连 sshd / journald** |
| **`StartLimitBurst=2`**<br>**`StartLimitIntervalSec=300`** | **限制重启次数** | 5 分钟内最多重启 2 次，超过就放弃。**没有它就会形成「OOM→重启→再 OOM」死循环，把整台盒子拖死** |
| `OOMScoreAdjust=500` | 提高被 OOM 选中的优先级 | 全局 OOM 时优先牺牲本服务，保护系统关键进程 |
| `RestartSec=60` | 重启间隔 | 间隔太短会在内存不足时反复加载权重、打满磁盘 IO |

### 设计说明

- **`WorkingDirectory=/root/llama.cpp` + `Environment=LD_LIBRARY_PATH=/root/llama.cpp/build/bin`**：`llama-server` 动态链接了同目录下的 `libllama.so` / `libggml*.so`，必须设置工作目录与库搜索路径，否则报 `error while loading shared libraries`。
- **`StandardOutput=append:` / `StandardError=append:`**：llama-server 的计时与请求日志输出到 stdout/stderr，追加写入独立日志文件便于排查。该日志会持续增长，需定期清理或轮转。
- **`Restart=on-failure` + `RestartSec=60` + `StartLimitBurst`**：崩溃后自动重启，但**必须同时限制重启次数**。只用 `Restart=on-failure` 而不管次数，一旦内存不足就会形成「进程被杀 → systemd 拉起 → 重新加载 532MB 权重 → 内存再爆 → 再被杀」的无限循环，磁盘 IO 被打满、load average 冲到 70 以上，连 sshd 都被饿死，表现就是**整机卡死**。不用 `Restart=always` 是因为正常停止（`systemctl stop`）不应被拉起。
- **`After=network.target`**：服务只监听本地 HTTP 端口，不需要外网，因此不依赖 `network-online.target`。
- **未设置 `User=root`**（与另外两个服务不同）：llama-server 不访问 `/dev/rknpu`、`/dev/dri/*` 等设备节点，用默认 root 运行仅为路径权限简单，也可改为普通用户。
- **注意：llama-server 不支持空闲自动卸载模型**，进程常驻不释放，具体内存数字见下一节。

### 内存预算与 OOM 防护

**盒子的内存是硬约束，必须按账配，配不平就会卡死。**

| 项 | 占用 |
| --- | --- |
| 盒子物理内存 | 3897 MB |
| sagesight 平台（含全部 worker） | ~1000 MB |
| llama-server（`-c 4096` + `--image-max-tokens 128` 下的推理峰值） | ~1050 MB |
| 系统 + ZLMediaKit + ffmpeg | ~300 MB |
| 图形桌面 gnome-shell + Xorg + gjs + portal | ~250 MB |
| **合计（保留桌面）** | **~2600 MB** |
| **合计（关闭桌面）** | **~2350 MB** |

llama-server 实测内存增长：

| 阶段 | 内存 |
| --- | --- |
| 启动完成 | 898 MB |
| 单图 + 4 图推理之后 | 1030 MB |

> **必须关闭图形桌面。** 盒子默认是 `graphical.target`，gnome-shell + Xorg + gjs + xdg-desktop-portal 常驻约 250MB。这台盒子是当服务器用的，应切到 `multi-user.target`：
>
> ```bash
> systemctl set-default multi-user.target
> systemctl stop gdm
> ```
>
> 关闭后实测 load average 从 69.76 降到 3.47，同时消除了 gnome / Mali GPU 的后台负载。之后盒子只能通过 SSH 操作。

**为什么 `-c` 和 `--image-max-tokens` 是内存开关**：llama-server 的内存 ≈ 权重（532MB + 205MB，基本固定）+ KV cache（正比于 `-c`）+ 视觉编码器图缓冲（正比于单图 token 数）。用 `-c 8192` + `--image-max-tokens 192` 时实测峰值冲到 **2.55GB**，叠加桌面环境必然 OOM；改成 `-c 4096` + `--image-max-tokens 128` 后峰值降到 **1.03GB**。

**三层防护各自管什么**：

1. **`MemoryMax=2400M`** —— 超限时只在本 cgroup 内 OOM 杀掉 llama-server，不再像全局 OOM 那样把 `journald`、`sshd` 一起带走
2. **`StartLimitBurst=2` + `StartLimitIntervalSec=300`** —— 5 分钟内失败 2 次就停止拉起，**彻底掐断重启死循环**
3. **`OOMScoreAdjust=500`** —— 万一发生全局 OOM，优先牺牲本服务，保护系统关键进程

**扩容提醒**：常见 RK3588 板子（如 `ztl A588`）的 LPDDR 是板载焊死的，**加内存条这条路走不通**。要根治只能换大内存板子，或把推理放到局域网另一台机器上。

## 七、启用步骤

按以下顺序在盒子上执行：

```bash
# 1. 写入服务文件
sudo nano /etc/systemd/system/qwen3.5.service
# 粘贴上面的内容，保存退出（Ctrl+O 回车保存，Ctrl+X 退出）

# 2. 重载 systemd
sudo systemctl daemon-reload

# 3. 启用开机自启
sudo systemctl enable qwen3.5.service

# 4. 立即启动
sudo systemctl start qwen3.5.service

# 5. 看状态（应为 active running）
sudo systemctl status qwen3.5.service

# 6. 看启动日志（确认出现 "server is listening" 且无报错）
tail -n 50 /root/qwen3.5-0.8b/service.log
```

### nano 粘贴注意事项

nano 默认会自动缩进，可能导致每行前面多出空格。粘贴前建议先关掉自动缩进：

- 按 `Alt + M`（或 `Esc` 然后按 `M`）切换掉 auto-indent
- 粘贴后检查每行开头是否有多余空格，有就删掉

> systemd 配置文件对行首空格不敏感，但 `[Unit]`/`[Service]` 这类段名必须顶格，不能有前导空格。

## 八、验证

### 1. 验证服务与端口

```bash
systemctl is-active qwen3.5.service    # 应输出 active
systemctl is-enabled qwen3.5.service   # 应输出 enabled
ss -tlnp | grep 8002
# 应看到 llama-server 监听 0.0.0.0:8002
```

### 2. 验证文本推理

```bash
curl -s http://127.0.0.1:8002/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"Qwen3.5-0.8B","messages":[{"role":"user","content":"你好"}],"max_tokens":32}'
```

返回的 `choices[0].message.content` **必须是正常文本**。如果 `content` 为空、而 `reasoning_content` 里有内容，说明 `--reasoning off` 没生效。

### 3. 验证图片推理（多模态）

用盒子上的测试脚本（`/root/qwen3.5-0.8b/tests/` 下已有 `snap640.jpg`）：

```bash
cd /root/qwen3.5-0.8b/tests
python3 -c "
import base64, requests, json
img = base64.b64encode(open('snap640.jpg','rb').read()).decode()
body = {
  'model': 'Qwen3.5-0.8B',
  'messages': [{'role':'user','content':[
      {'type':'text','text':'用一句话描述这张图片'},
      {'type':'image_url','image_url':{'url':'data:image/jpeg;base64,'+img}}
  ]}],
  'max_tokens': 128

print(r.json()['choices'][0]['message']['content'])
"
```

应返回对图片的有效中文描述。

### 4. 验证开机自启

重启盒子验证一次最稳：

```bash
sudo reboot
# 重启后等 30 秒登录
systemctl status qwen3.5.service   # 应为 active (running)
```

`Loaded: ... enabled` 表示开机自启已启用，`Active: active (running)` 表示服务正在运行。其自启机制与 `sagesight.service`、`zlmediakit.service` 完全一致（`multi-user.target.wants` 下的软链接）。

## 九、平台侧接入

盒子上的服务只是推理后端，平台还需在数据库里有一条指向它的配置，并打开总开关。

### 1. 图形界面配置（推荐）

登录平台 → **系统管理 → 大模型配置** → 新增：

| 字段 | 填写值 | 说明 |
| --- | --- | --- |
| 配置名称 | `Qwen3.5-0.8B 盒子本地` | 任意 |
| API 格式 | `openai` | llama-server 兼容 OpenAI 格式 |
| **API base URL** | **`http://127.0.0.1:8002/v1`** | **必须带 `/v1` 结尾，见下方说明** |
| API 密钥 | 留空 | 本地服务不校验 |
| 模型名称 | `Qwen3.5-0.8B` | 与服务的 `--alias` 一致 |
| 温度 | `0.3` | — |
| 最大输出 token | `512` | — |
| 支持图片输入 | ✅ 开启 | 关闭会降级为纯文本，描述/去重失效 |
| 启用事件描述 | ✅ 开启 | — |
| 启用语义去重 | ✅ 开启 | — |
| 设为默认 | ✅ 开启 | 平台只读默认配置 |

然后在页面上方的**「大模型功能总开关」**打开（对应 `system_settings.llm_enabled = 1`）。

### 2. 关键说明：base_url 必须带 `/v1`

平台客户端拼接 URL 的逻辑是 `{base_url}/chat/completions`。因此：

- 填 `http://127.0.0.1:8002` → 实际请求 `http://127.0.0.1:8002/chat/completions` → **404**
- 填 `http://127.0.0.1:8002/v1` → 实际请求 `http://127.0.0.1:8002/v1/chat/completions` → ✅

### 3. 修改配置后必须重启平台服务

大模型服务只在**进程启动时初始化一次**（`TrackedObjectProcessor.__init__` 中调用 `_init_llm`），且初始化时**不发网络请求**，只构造客户端对象。所以：

```bash
# 改完配置/总开关后，必须重启才生效
sudo systemctl restart sagesight.service

# 确认初始化成功
journalctl -u sagesight.service -n 50 --no-pager | grep 大模型
```

预期看到：

```
大模型事件处理已启用: model=Qwen3.5-0.8B, provider=openai, description=on, semantic_dedup=on
```

若看到的是 `大模型功能总开关已关闭...` 或 `未配置默认大模型...`，说明总开关未开或没有默认配置。

### 4. 端到端验证

**前置条件：必须真的产生一次事件**。平台的调用链是「检测到目标 → 生成事件 → 事件描述/语义去重」，**画面里没有目标就没有事件，也就不会调用大模型**。这一点极易误判为「接入失败」，排查时先确认事件表非空：

```bash
# 确认有事件产生（结果为 0 说明还没触发过，不是配置问题）
python3 -c "
import sqlite3
c = sqlite3.connect('/root/sagesight-ai/data/tasks.db')
print(c.execute('select count(*), max(created_at) from events').fetchone())
"
```

有事件后，用下面两条命令确认调用链：

```bash
# 1. 平台侧：事件描述/去重的调用日志
journalctl -u sagesight.service | grep -e EventDescriber -e EventDedup

# 2. 模型侧：已处理的请求数（每次请求一行 launch_slot_，数字 > 0 表示平台确实打进来了）
grep -c launch_slot_ /root/qwen3.5-0.8b/service.log
```

### 5. 回滚

保留一条外部大模型配置（如阿里云 MaaS / 局域网 `Qwen3-VL-2B-Instruct`）不删除，需要时在页面上「设为默认」并重启 `sagesight.service` 即可切回。平台只读默认配置，切换不需要改代码。

## 十、日志说明

存在三份日志，用途不同：

| 日志来源 | 查看命令 | 内容 |
| --- | --- | --- |
| 模型服务日志 | `tail -f /root/qwen3.5-0.8b/service.log` | llama-server 运行日志：模型加载、请求计时（prompt eval / eval tok/s）、错误 |
| journald（模型） | `journalctl -u qwen3.5.service -f` | systemd 收集的 stdout/stderr，与 service.log 内容一致 |
| 平台业务日志 | `tail -f /root/sagesight-ai/logs/system.log` | 事件产生、描述/去重结果、调用失败重试 |

- 排查「平台有没有调进来」：`grep -c launch_slot_ /root/qwen3.5-0.8b/service.log`（每次请求记一行）
- 排查「模型快不快」：看 `service.log` 里的 `print_timing` 行（`prompt eval time` 是视觉编码耗时，是主要瓶颈）
- 排查「平台调用失败」：看 `system.log` 与 `journalctl -u sagesight.service`（客户端 120s 读超时会抛 `OpenAI API 请求失败`）

> `service.log` 由 append 模式写入，不会自动滚动，长期运行需定期清理：`: > /root/qwen3.5-0.8b/service.log`

## 十二、故障排查

### 服务起不来

```bash
systemctl status qwen3.5.service
tail -n 50 /root/qwen3.5-0.8b/service.log
```

### 典型问题对照表（均为本次部署实测遇到）

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| 推理极慢，0.09 tok/s | 用了 PyTorch 方案 | 必须改 llama.cpp + GGUF，见第一章 |
| `couldn't bind HTTP server socket, port 8002` | 已有手工 `nohup` 实例占着端口 | `systemctl stop` 后用 `ps -eo pid,args` 找到 PID 精确 kill，再启动服务 |
| `error while loading shared libraries: libllama.so` | 缺少库搜索路径 | 服务文件加 `Environment=LD_LIBRARY_PATH=/root/llama.cpp/build/bin` |
| API 返回正常但 `content` 为空 | 模型处于思考模式，内容落在 `reasoning_content` | ExecStart 加 `--reasoning off`；平台只读 `content` |
| 1920×1080 单图推理 74 秒 | 视觉预填充耗时 69 秒，未限制图像 token | ExecStart 加 `--image-max-tokens 128` |
| 多图请求返回 `400 Bad Request` | `-c` 装不下多张图的 image token | 优先调小 `--image-max-tokens`（4 图 × 128 ≈ 512 token，`-c 4096` 已足够）；实在不够再调大 `-c`，但要付出内存代价 |
| 返回 `404 not found` | `base_url` 少写了 `/v1` | 改为 `http://127.0.0.1:8002/v1` |
| 平台完全不调用模型（`grep -c launch_slot_ service.log` = 0） | **没有任何事件产生**，或总开关关闭，或改配置后未重启 | 先确认 `events` 表非空；确认 `llm_enabled=1`；`systemctl restart sagesight.service` |
| 改了配置不生效 | `_init_llm` 只在进程启动时执行一次 | 必须重启 `sagesight.service` |
| 模型无法识图，只输出文本 | 漏了 `--mmproj`，或平台「支持图片输入」未开 | 补 `--mmproj`；页面勾选「支持图片输入」 |
| 访问 `/api/system/llm-configs` 返回 401 | 该接口需要登录会话 | 从平台页面操作，或直接改数据库 |
| **整机卡死、SSH 连不上（但 ping 通）** | **OOM → `Restart=on-failure` 无限重启死循环，磁盘 IO 与负载被打满，sshd 被饿死** | 见下文「系统卡死（OOM 重启死循环）」 |

### 服务运行但平台调用失败

```bash
# 平台侧
tail -n 100 /root/sagesight-ai/logs/system.log
journalctl -u sagesight.service | grep -i llm

# 模型侧
grep -c launch_slot_ /root/qwen3.5-0.8b/service.log
tail -n 30 /root/qwen3.5-0.8b/service.log
```

常见原因：

- **客户端超时**：请求超时是连接 10s / 读取 120s。多图去重较慢（4 图实测约 19.8s），若图片过大或并发过高可能超时，可调小 `--image-max-tokens`。
- **上下文不足**：图片越多占用越大，必要时调大 `-c`（代价是更多内存）。
- **服务未监听 0.0.0.0**：若用 `--host 127.0.0.1`，只有本机能访问，跨机调用需 `--host 0.0.0.0`。

### 系统卡死（OOM 重启死循环）

**症状**：整机无响应，SSH 连不上（报 `Error reading SSH protocol banner`），但 `ping` 通——说明内核还活着，只是 swap 抖动把 sshd 饿死了。

**定位**：

```bash
uptime                                       # load average 会高得离谱（实测冲到 69.76）
systemctl show qwen3.5.service -p NRestarts  # 数值很大说明在反复重启
dmesg | grep -i oom | tail -20               # 找 OOM killer 记录
```

典型的 OOM 记录长这样：

```
Out of memory: Killed process 465135 (llama-server) anon-rss:2554020kB
systemd[1]: qwen3.5.service: Main process exited, code=killed, status=9/KILL
systemd[1]: systemd-journald.service: Main process exited, code=killed, status=9/KILL
```

最后一行是关键——**连 `journald` 都被连带杀掉了**，说明当时是全局 OOM，不是 cgroup 内 OOM。

**恢复（按顺序执行）**：

```bash
# 1. 打断死循环：停服务即可，systemd 不会再把正常停止的服务拉起来
systemctl stop qwen3.5.service

# 2. 确认已停、内存已回落
systemctl is-active qwen3.5.service    # 应为 inactive
free -m                                # used 应大幅下降

# 3. 关掉图形桌面，省出约 250MB
systemctl set-default multi-user.target
systemctl stop gdm

# 4. 确认服务文件里三层防护都在（缺了就按第六章补）
grep -e MemoryMax -e StartLimitBurst /etc/systemd/system/qwen3.5.service

# 5. 无误后再启动
systemctl start qwen3.5.service
```

> **不要用 `swapoff -a` 去"清 swap"**。它要求把 swap 里的内容全部读回物理内存，内存本来就不够，执行后大概率直接把系统拖死。只有等 `available` 大于 swap 已用量时做才安全。

**预防**：`MemoryMax` + `StartLimitBurst` + 关闭图形桌面，三者缺一不可，详见第六章「内存预算与 OOM 防护」。

### 内存不足的日常处理

```bash
free -m
systemctl show qwen3.5.service -p MemoryCurrent -p MemoryMax
```

模型常驻约 0.9-1.1GB 且**不会自动卸载**。若盒子内存紧张：

- 确认 4GB swap 已启用（`swapon --show`）
- 确认图形桌面已关闭（`systemctl get-default` 应输出 `multi-user.target`）
- 优先调小 `--image-max-tokens`（对内存峰值影响最大），不够再调小 `-c`
- 检查平台侧是否异常增长：`systemctl show sagesight.service -p MemoryCurrent` 长期应稳定在 1GB 左右

### 磁盘空间不足

```bash
df -h /
```

模型 + 编译产物合计约 1.3GB，另有 swap 文件 4GB。若空间不足，可清理不再需要的文件（例如旧的 `venv/`、HF safetensors 等遗留物）。

## 十三、性能实测数据

以下为本次部署在 RK3588 上的实测值，供容量评估参考：

| 场景 | `-c 8192` + `--image-max-tokens 192`（调优前） | `-c 4096` + `--image-max-tokens 128`（当前） |
| --- | --- | --- |
| llama-server 启动常驻内存 | 1.09 GB | **0.90 GB** |
| 单图 + 4 图推理后内存 | 2.55 GB（触发 OOM） | **1.03 GB** |
| 纯文本请求 | 0.9 s | 0.9 s |
| 单图 640×640（事件描述） | 7.3-8.0 s | **5.4 s** |
| 4 图语义去重 | 19.8 s | **14.4 s** |
| 单图 1920×1080（未限制图像 token） | 74.3 s | — |

**瓶颈是视觉编码（ViT forward），不是文本生成**。图像 token 数近似为 `(宽/32) × (高/32)`，所以图片越大越慢、内存峰值也越高。**`--image-max-tokens` 同时是延迟开关和内存开关**，调它比调 `-c` 划算。
